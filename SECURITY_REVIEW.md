те# Проверка безопасности auth-spring-boot-starter

> Исторический снимок до исправлений. Текущее состояние: [SECURITY_FIX_STATUS.md](SECURITY_FIX_STATUS.md).

Дата: 2026-09-28. Commit: `11d8dbf`. Артефакт: `kz.innlab:auth-spring-boot-starter:0.1.2`.

## Вывод

В текущем состоянии starter нельзя рекомендовать как безопасную замену Keycloak для общего использования в компании. Подтверждён захват существующего аккаунта без пароля через публичную регистрацию. Подтверждена привязка номера телефона без проверки владения именно этим номером. Обновление сторонних библиотек эти ошибки не исправит.

Практическое преимущество starter — готовые бизнес-интеграции и установка как Maven dependency. Для централизованной идентификации нескольких приложений предпочтителен поддерживаемый и правильно настроенный Keycloak. Уведомления, SMTP, Firebase и бизнес-права разумно оставить в приложениях.

## Метод и границы проверки

- Просмотр реализации регистрации, social login, смены реквизитов, токенов, Spring Security, rate limiting, административных операций, уведомлений и CI.
- Разрешено Maven dependency tree; 242 compile/runtime координаты проверены через OSV API. Собственный артефакт не отправлялся в OSV.
- Бюллетени Spring, Apache Tomcat и Netty сверены с официальными источниками.
- Локально на JDK 26/H2 выполнены `SecurityIntegrationTest` (8), `RefreshTokenRotationTest` (9) и два временных теста воспроизведения (2). Все 19 завершились без ошибок. Два новых теста намеренно проверяли наличие уязвимого поведения: их успешность подтверждает ошибки.
- Production-код и pom.xml не изменены. Временный тест удалён из src/test после выполнения; копия сохранена в `target/security-audit/SecurityAuditReproductionTest.kt`.
- Это проверка исходников и локальных сценариев, не полный pentest. Production, reverse proxy, реальные IDP, браузерные атаки, история секретов, нагрузочные и конкурентные сценарии не проверялись. Test/build зависимости и скрытые внутри JAR компоненты полностью не сканировались. Отсутствие OSV-совпадения не гарантирует отсутствие CVE.

## Подтверждённые проблемы

### F1 — Critical: захват аккаунтов без пароля

Файлы: `src/main/kotlin/kz/innlab/starter/authentication/service/LocalAuthService.kt:44`, `authentication/controller/LocalAuthController.kt:38`, `config/SecurityConfig.kt:61` (последние два пути относительно `src/main/kotlin/kz/innlab/starter/`).

Публичный `/api/v1/auth/local/register` находит существующего пользователя по email. Если passwordHash отсутствует, присваивает переданный пароль, добавляет LOCAL и выдаёт токены. Проверки текущей сессии или нового подтверждения email нет. Это затрагивает Google/Apple и email-OTP аккаунты с email и без пароля. Роли пользователя сохраняются, поэтому возможен захват административного аккаунта при тех же условиях.

Тест: создан фиктивный GOOGLE-пользователь; регистрация без Authorization вернула 201, новый пароль сохранился; последующий login с ним вернул 200.

`registration.enabled=false` не закрывает эту ветку: проверка флага находится только в создании нового пользователя. Включение email verification тоже её не закрывает.

Исправление: публичная регистрация не должна менять существующий аккаунт. Добавление пароля — отдельная операция после подтверждения личности владельца. До исправления закрыть этот маршрут на публичном входе либо отключить local provider с учётом влияния на текущих пользователей.

### F2 — High: OTP смены телефона не связан с сохраняемым номером

Файл: `src/main/kotlin/kz/innlab/starter/authentication/service/AccountManagementService.kt:210`.

При запросе OTP номер сохраняется как `VerificationCode.newValue`. При подтверждении метод проверяет код, пользователя и purpose, но игнорирует newValue и сохраняет номер из нового запроса.

Тест: код выпущен для фиктивного номера A; HTTP verify с этим кодом и номером B вернул 200 и сохранил B. Реальная SMS не отправлялась. Номер B должен быть ещё не занят: проверка уникальности существует. Это позволяет выдавать чужой свободный номер за подтверждённый и нарушает идентификацию по телефону; прямой захват уже зарегистрированного по телефону аккаунта этим тестом не доказан.

Исправление: сохранять только номер из проверенной записи newValue; альтернативно строго сравнивать его с нормализованным номером запроса.

## Другие риски по исходникам

### F3 — High при достижении ёмкости: rate limiter пропускает все запросы

`src/main/kotlin/kz/innlab/starter/shared/ratelimit/InMemoryRateLimiter.kt:31`: после заполнения 100 000 ключей возвращается true, в том числе для уже ограниченных ключей. Login позволяет задавать ключ через email. Масштабная эксплуатация не воспроизводилась; скорость заполнения зависит от инфраструктуры. Счётчики также отдельные на каждом экземпляре.

Исправление: общий Redis/другой атомарный store, безопасная политика при заполнении, ограничения по IP и аккаунту. Не снимать защиту существующих ключей при исчерпании памяти.

### F4 — Medium, зависит от конфигурации: cookie auth без CSRF-токенов

`config/SecurityConfig.kt:44` отключает CSRF безусловно, а `config/AuthCookieProperties.kt` допускает cookie authentication и SameSite=None. По умолчанию cookie mode выключен, при включении SameSite=Strict и Secure=true — полезные ограничения. Реальная CSRF-достижимость зависит от Origin/CORS, типа запроса, браузера и доверенных поддоменов; браузерного воспроизведения нет.

Исправление: при cookie mode включать CSRF-защиту для меняющих состояние операций. CORS и SameSite учитывать как дополнительные ограничения, не как универсальную замену проверке CSRF.

### F5 — Medium, при совместном использовании ключей: нет проверки назначения JWT

`config/RsaKeyConfig.kt:75`: decoder создаётся без прикладных issuer/audience validators. `authentication/service/TokenService.kt:27`: issuer одинаковый `template-app`, audience отсутствует. Подпись и стандартные временные проверки не заменяют изоляцию получателей. Риск межсервисного использования токенов возникает при общих доверенных ключах; произвольную подпись это не позволяет подделать.

Исправление: конфигурируемый issuer, audience, их обязательная проверка; отдельные ключи по средам и границам доверия.

### F6 — Medium: уже выданные JWT сохраняют старые полномочия

`user/service/AdminUserService.kt:127` меняет роли в БД, а SecurityConfig принимает роли из JWT. Сброс пароля отзывает refresh tokens, но существующий access token продолжает действовать до exp с учётом допустимого clock skew. Номинальный TTL — 15 минут. Это архитектурный компромисс stateless JWT, а не уникальная проблема этого проекта: при локальной проверке JWT Keycloak тоже не обеспечивает мгновенный отзыв автоматически.

Если нужен немедленный отзыв: session/token version с проверкой на запросе, introspection или denylist, особенно для административных операций.

### F7 — Риск identity linking: Google-пользователь ищется по email

`authentication/service/GoogleOAuth2Service.kt:25` не проверяет email_verified перед передачей email в `UserService.findOrCreateGoogleUser`. Там существующий аккаунт выбирается по email, providerId записывается заново. Для Google предпочтителен стабильный sub. Необходима отдельная политика связывания существующих аккаунтов с повторным подтверждением владельца. Эксплуатация через реального провайдера не проверялась.

### F8 — Пробел контроля обновлений и несовпадение JDK в CI

`.github/workflows/ci.yml:22` использует JDK 24, тогда как pom.xml задаёт Java 25. Такой CI не соответствует целевому bytecode; локальная проверка была на JDK 26. В просмотренном workflow нет SCA/security scan, в .github нет Dependabot-конфигурации.

Исправление: согласовать JDK, добавить регулярный SCA/SBOM и автоматические PR обновлений. Сканировать также итоговое приложение-потребитель: его dependencyManagement может поменять версии starter.

## Сторонние зависимости

Разрешённые версии: Spring Boot 4.1.1, Spring Security 7.1.1, Spring Framework 7.0.9, Spring Data JPA 4.1.1, Tomcat 11.0.24, Nimbus JOSE JWT 10.9.1, Firebase Admin 9.4.3, Google libraries-bom 26.55.0, grpc-netty-shaded 1.69.0.

OSV вернул четыре advisory для двух координат:

| Компонент | Совпадения | Применимость |
|---|---|---|
| tomcat-embed-core 11.0.24 | CVE-2026-65905, CVE-2026-65182, CVE-2026-68525 | Затрагивают DIGEST/FORM/container constraints. В этом проекте JWT через Spring Security; перечисленные режимы не обнаружены. Наличие версии подтверждено, эксплуатация здесь — нет. |
| grpc-netty-shaded 1.69.0 | CVE-2025-55163 | HTTP/2 server DoS. Зависимость приходит через Firebase/Google Cloud; входящий gRPC server в просмотренном коде не найден. Это совпадение версии, не доказательство доступной извне атаки. |

Официальный [бюллетень Apache Tomcat](https://tomcat.apache.org/security-11.html) содержит дополнительные свежие исправления, отсутствовавшие в ответе OSV: например HTTP/2 header mix-up CVE-2026-86350, исправленный в 11.0.26. Поэтому четыре совпадения OSV нельзя считать полным числом CVE. Обновить согласованную линейку Tomcat минимум до 11.0.26 или более свежего совместимого исправленного релиза, предпочтительно через Boot BOM. Применимость HTTP/2 зависит от конфигурации сервера.

[Netty advisory](https://github.com/netty/netty/security/advisories/GHSA-prj3-ccx8-p6x4) описывает CVE-2025-55163; [gRPC 1.75.0](https://github.com/grpc/grpc-java/releases/tag/v1.75.0) обновляет Netty с исправлением. Поднимать Google BOM/Firebase/gRPC согласованно. Обновление обычного io.netty отдельно не заменяет копию внутри shaded JAR.

Spring Security 7.1.1 уже является исправленной версией для [CVE-2026-41707](https://spring.io/security/cve-2026-41707/) и [CVE-2026-47841](https://spring.io/security/cve-2026-47841/); Spring Data JPA 4.1.1 — для [CVE-2026-47834](https://spring.io/security/cve-2026-47834/). Эти CVE не следует приписывать текущей сборке.

## Что сделано правильно

- Spring Security и стандартный PasswordEncoder с bcrypt по умолчанию; собственная криптография паролей не изобретена.
- RSA-подпись access tokens; случайные 256-битные refresh tokens хранятся как SHA-256 hashes.
- Ротация refresh tokens, обработка повторного использования, независимая транзакция отзыва.
- OTP генерируются SecureRandom, хешируются, имеют срок и счётчик попыток.
- Административные маршруты, topic broadcast и общий IMAP ограничены ролью ADMIN.
- Push по отдельным токенам проверяет принадлежность устройств; есть лимиты почты и вложений.
- При профиле prod есть проверки опасных dev-code и console fallbacks.

Эти меры полезны, но не компенсируют F1/F2. Конкурентная одноразовость OTP отдельно не доказана: чтение used/attempts и обновление выполняются раздельно; требуется отдельная проверка параллельных запросов.

## Сравнение с Keycloak

| Критерий | Этот starter | Keycloak |
|---|---|---|
| Подключение одного Spring-приложения | Maven dependency, нет отдельного IAM-сервера | Нужен отдельный сервис и его эксплуатация |
| SSO нескольких приложений | Собственный JWT API; полноценная настройка OIDC authorization server в просмотренном коде не найдена | OIDC/SAML, централизованные клиенты и сессии |
| MFA, TOTP, passkeys | Встроенная реализация не найдена; вход по SMS/email не равен MFA | Готовые настраиваемые механизмы |
| LDAP/AD, identity federation | Не найдены | Поддерживаются |
| Telegram, WhatsApp, Firebase, бизнес-почта | Готовые специфичные интеграции | Для таких бизнес-функций нужны отдельные интеграции/сервисы |
| Ответственность за auth-логику | Ваша команда исправляет все сценарии и поддерживает их в каждом потребителе | Основную IAM-реализацию сопровождает проект; конфигурация и обновления остаются вашей задачей |
| Гибкость бизнес-прав | Полный контроль в коде | Приложения всё равно должны проверять доступ к своим объектам |

Возможности Keycloak сверены по [Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/). У Keycloak есть [процесс обработки уязвимостей](https://www.keycloak.org/security), но это не гарантия безопасности любой установки: нужны обновления и правильные настройки.

Для нескольких продуктов компании рекомендована схема: Keycloak отвечает за личности, вход и MFA; Spring-приложения проверяют issuer/audience/подпись и бизнес-права; этот starter сохраняет полезные notification-интеграции после отделения от собственного login/token issuance. Telegram/WhatsApp потребуют отдельного проектирования интеграции.

Если приложение одно и собственные способы входа важнее SSO, starter можно развивать, но сначала закрыть F1/F2, затем пересмотреть identity linking, rate limiting, cookies/JWT и поставить обновления под CI-контроль. Процент «безопаснее Keycloak» по этой проверке вычислить нельзя.
