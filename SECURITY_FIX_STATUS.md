## Осталось решить и проверить

### Новые находки повторной проверки

- **Высокий риск: замена фактора входа по одному access token.** `AccountManagementService.requestEmailChange`/`verifyEmailChange` и аналогичные методы для телефона требуют только JWT и код, отправленный на новый контакт. Владелец украденного access token может указать собственный email/номер, подтвердить его и получить новые токены через включённые по умолчанию email/phone OTP endpoints. Пароль и прежний контакт не нужны; refresh tokens после смены не отзываются. Требуются повторная аутентификация существующим фактором, подтверждение нового контакта, уведомление старого контакта и отзыв сессий. Добавить регрессионный тест этой цепочки.
- **Политика доступа: email OTP даёт роли существующего аккаунта.** `UserService.findOrCreateEmailOtpUser` возвращает пользователя с совпавшим email, включая `ADMIN`; `/auth/email/verify` выдаёт токены с его ролями. Это ожидаемая логика passwordless, но почта становится единственным фактором и для admin/local/social аккаунтов. Решить, кому разрешён такой вход; для привилегированных аккаунтов отключить его либо требовать дополнительный фактор.
- **Не подтверждена безопасность конкурентного refresh.** `RefreshTokenService.rotate` читает старый token без блокировки, создаёт замену, затем помечает старый revoked. `@Version` должен прервать одну конкурентную транзакцию, но PostgreSQL теста нет. Проверить, что остаётся ровно одна действующая ветка.

1. **F6, отзыв уже выданных JWT.** Снятие роли, сброс пароля и удаление пользователя не останавливают ранее выданный access token сразу. Текущий TTL 15 минут плюс допустимый clock skew. Для немедленного отзыва нужны token/session version, introspection или denylist с проверкой при запросе. Выбрать допустимое окно для продукта.
2. **Кластерный rate limiting.** In-memory реализация защищена от fail-open, но счётчики отдельны на каждом экземпляре. Для нескольких реплик заменить bean `RateLimiter` общим атомарным хранилищем и проверить сбои этого хранилища. При заполнении локальной ёмкости новые пользователи могут получить 429: это явный компромисс доступности.
3. **Cookie mode в браузере.** MockMvc проверяет 403 без/с неверным CSRF token и успех с правильным. Провести проверку реальным браузером через reverse proxy, особенно при SameSite=None, доверенных поддоменах и смешанных bearer/cookie клиентах. Login без auth cookie не требует CSRF; оценить login CSRF для конкретного клиента.
4. **Миграции существующей БД.** V11–V13 корректно падают при исторических дубликатах, чтобы не объединять или удалять аккаунты автоматически. До rollout проверить дубликаты `(provider,provider_id)`, `(identifier,purpose)` и `lower(email)` для непустых адресов; согласовать удаление только устаревших кодов. Проверить Flyway history/checksums на копии production-схемы.
5. **Совместимость клиента.** Старые access tokens без `aud` перестают работать после обновления; клиенту нужен повторный вход либо новый access token через refresh. Google/Apple вход с email существующего аккаунта теперь возвращает 409; публичная регистрация больше не добавляет пароль social-аккаунту. Нужен отдельный безопасный owner-verified linking flow, если функция требуется.
6. **Ключи и production.** Настроить постоянный PKCS12 keystore, уникальные `JWT_ISSUER`/`JWT_AUDIENCE` и общие публичные ключи между репликами. Ротация нескольких ключей с переходным окном ещё не реализована. Внешний путь к файлу передавать как `file:/absolute/path`.
7. **Остальные пункты плана.** Реальные Telegram/SMTP/Firebase endpoints, browser flow, конкурентная refresh rotation на PostgreSQL, per-account/IP лимиты и финальное приложение-потребитель требуют отдельной интеграционной проверки. Прохождение тестов starter не доказывает безопасность конфигурации потребителя.

Исходный аудит фиксирует проблемы до этой работы. Изменения не развёрнуты и не опубликованы как Maven artifact.
