# План устранения рисков безопасности — передача другой модели

> Часть этапов уже выполнена после составления плана. Фактический статус: [SECURITY_FIX_STATUS.md](SECURITY_FIX_STATUS.md).

Основание: `SECURITY_REVIEW.md`, проверка 2026-09-28, commit `11d8dbf`.
Проект: `kz.innlab:auth-spring-boot-starter`, Kotlin / Spring Boot / Maven.

## Задание исполнителю

Исправить подтверждённые дефекты авторизации, проверить оставшиеся риски, обеспечить регрессионные тесты и контроль зависимостей. Работать этапами ниже. Сначала изучить текущие AGENTS.md, исходники и изменения пользователя: номера строк и состояние после аудита могут измениться.

Этот документ — план, а не выполненные исправления. Production-код во время аудита не менялся. Не считать старые успешные тесты доказательством безопасности.

Правила выполнения:

- F1 и F2 подтверждены локальными HTTP-тестами. Остальные пункты имеют разную степень подтверждения; сначала воспроизвести риск или обосновать применимость.
- Сначала написать тест, который требует безопасного поведения и падает на текущем коде. Затем исправить реализацию и получить успешный результат.
- Старые audit-тесты проверяли наличие уязвимости: их нельзя просто включить в CI как «security tests». Их утверждения нужно заменить на безопасные ожидания.
- Использовать синтетические аккаунты, локальные БД и тестовые отправители. Не отправлять реальные SMS/email/push и не атаковать production.
- Сохранить авторизацию по ролям, required actions, отключение провайдеров, bean overrides и контракты starter для приложений-потребителей.
- Не включать автоматический публичный account linking по совпадению email в качестве совместимости.
- Не выполнять переход на Keycloak, публикацию артефакта или deployment в рамках исправления без отдельного решения пользователя.
- Для изменений API, конфигурации и БД описывать переход потребителей и совместимость старых токенов.
- Каждый этап завершать кратким результатом: файлы, тесты, устранённые риски, ограничения. Не объявлять неподтверждённый риск устранённым только по чтению кода.

Все сокращённые пути Kotlin ниже относятся к `src/main/kotlin/kz/innlab/starter/`.

## 1. F1: запретить захват аккаунта через регистрацию

Посмотреть:

- `authentication/controller/LocalAuthController.kt`.
- `user/repository/UserRepository.kt`, `user/model/User.kt`.
- `src/test/kotlin/kz/innlab/starter/LocalAuthIntegrationTest.kt`.

Изменить:

1. Публичный register создаёт только новый аккаунт. Для существующего email не меняет пароль, providers, roles, имя и не выдаёт токены. Для минимального исправления использовать существующий контракт 409; унификация ответов против enumeration — отдельное изменение.
2. Удалить ветку установки пароля существующему social/passwordless пользователю.
3. `registration.enabled=false` не должен оставлять обход через существующего пользователя.
4. Проверить нормализацию email и ограничения уникальности БД. Не вводить глобальный lowercase/новый unique index без поиска коллизий и плана миграции. Не сливать аккаунты автоматически.
5. Если добавление пароля нужно продукту, вынести в отдельную операцию с подтверждением личности: свежая повторная аутентификация или одноразовое подтверждение, связанное с текущим пользователем и назначением операции. Самого знания email или наличия старого access token недостаточно для выбранной строгой политики.

Проверить:

- Существующие GOOGLE, APPLE, email-OTP аккаунты без passwordHash: анонимный register отклонён; все поля и количество refresh tokens неизменны.
- Аналогичный аккаунт ADMIN: ни выдачи токенов, ни изменения credentials.
- Проверить при включённой/выключенной регистрации и email verification.
- Обычный новый пользователь регистрируется, проходит verification и входит согласно текущему контракту.
- Повторные и конкурентные регистрации не создают две личности с одним каноническим email.

Готово: ни одна ветка публичной регистрации не присваивает credentials существующему аккаунту.

## 2. F2: связать OTP с номером телефона

- `authentication/service/VerificationCodeService.kt`.
- `authentication/dto/VerifyChangePhoneRequest.kt`.

Изменить:

1. Источник нового номера — `newValue` проверенной записи OTP.
2. Для минимального совместимого исправления сохранить phone в DTO, нормализовать и сравнить с newValue; при несовпадении отклонить запрос. После проверки сохранять значение из записи.
3. Не принимать null/пустой newValue. Старые незавершённые записи без newValue отклонять с предложением запросить новый код.
4. Сохранить проверки пользователя, purpose, срока, использованности, попыток и уникальности номера. Гонку уникальности закрывает также constraint БД.

Проверить:

- OTP для A + verify с B → 4xx, телефон не изменён.

- Код другого пользователя/назначения, истёкший и использованный код → отказ.
- Занятый номер → отказ без повреждения аккаунтов.

Готово: номер невозможно изменить на значение, владение которым не доказано данным OTP.

## 5. F3 и дополнительная проверка: rate limits, OTP, refresh

Посмотреть:

- `shared/ratelimit/*`, `config/RateLimitProperties.kt`, `LocalAuthService`.
- `VerificationCodeService`, `VerificationAttemptRecorder`, `VerificationCodeRepository`.
- `RefreshTokenService`, `RefreshTokenFamilyRevoker`, `RefreshTokenRepository`, BaseEntity.
- PhoneOtpService, EmailOtpService, TelegramAuthService и обработку клиентского IP.

Изменить подтверждённый fail-open:

- При заполнении in-memory map существующие ограничения продолжают работать. Для новых ключей — ограниченная безопасная политика, не безусловный allow.
- Окно/expiry хранить корректно для каждого ключа: очистка не должна применять окно текущего запроса к чужим правилам.
- Для нескольких экземпляров предоставить общий атомарный limiter, например Redis. Не делать Redis обязательным для всех потребителей без явного решения о совместимости.
- Ограничивать аккаунт и источник запросов; доверять forwarded IP только от настроенных proxy. Проверить registration, forgot-password, OTP issuance, verification и платные каналы.
- Определить поведение при сбое общего limiter: аутентификация не должна незаметно становиться неограниченной; возвращать согласованную контролируемую ошибку.

Проверить конкурентность до выбора исправления:

- Параллельные OTP-проверки сейчас читают состояние отдельно от обновления. На PostgreSQL синхронно запустить несколько запросов на один код. Результат успешного потребления — не более одного раза.
- Параллельные неверные коды не обходят max attempts; счётчик сохраняется после rollback.
- Параллельная отправка кодов не обходит cooldown и не вызывает несколько платных доставок сверх политики.
- При подтверждённой гонке использовать условный атомарный update/корректную блокировку, проверять affected rows. Не добавлять блокировку внешней транзакции поверх REQUIRES_NEW без анализа deadlock.
- Параллельная refresh rotation не создаёт две действующие ветки. Reuse за grace window отзывает нужные токены несмотря на исключение. Ошибка доставки ответа/повтор клиента имеет документированный исход.

Тесты limiter выполнять с маленькой ёмкостью и управляемыми часами; кластерный вариант — на двух экземплярах с общим store. H2 недостаточно для доказательства PostgreSQL transaction semantics.

Готово: ограничения нельзя отключить заполнением, конкурентные операции не нарушают одноразовость, платные отправки ограничены.

## 6. F4: cookie authentication и CSRF

Посмотреть: SecurityConfig, AuthCookieProperties, CookieBearerTokenResolver, AuthCookieWriter, AuthResponseCookieAdvice, AuthController, cookie/consumer tests, раздел README о CSRF.

Изменить:

- Для cookie-authenticated меняющих состояние операций включить стандартную CSRF-защиту Spring Security и описать получение/передачу CSRF token клиентом.
- Отдельно обработать refresh/logout/revoke: они читают refresh cookie даже без access token. Нельзя исключить весь `/api/v1/auth/**` из CSRF только потому, что он permitAll.
- Явно определить поведение смешанного режима. Authorization header на resource-запросе не должен случайно освобождать от CSRF операцию, которая фактически использует refresh cookie.
- Bearer-only клиенты без автоматических credentials могут иметь отдельное правило; доказать отсутствие cookie fallback в исключаемой ветке.
- Валидировать cookie-настройки, включая SameSite=None + Secure, одинаковые атрибуты установки/очистки, HttpOnly для auth cookies. Обновить README и клиентский контракт.

Проверить: cookie-запрос без/с неверным CSRF → 403; с корректным → успех; refresh без действующего access cookie тоже защищён; logout очищает cookies; bearer-only flow работает; посторонние origins отклоняются. Выполнить браузерный сценарий с двумя origins и реальными cookies, учитывая SameSite, preflight и multipart, а не только MockMvc.

Готово: безопасность cookie mode подтверждена тестами и браузером; режим совместимости не оставляет обхода.

## 8. F6: отзыв доступа — принять и реализовать политику

Сначала выяснить требование продукта: допускается ли доступ до exp после удаления пользователя, снятия ADMIN или сброса пароля? Это архитектурное решение. Не обещать мгновенный отзыв stateless JWT и не считать переход на Keycloak автоматическим решением.

Для строгого варианта: session/token version в БД или общем store, проверка версии/состояния пользователя на защищённых запросах. Определить cache TTL, максимально допустимую задержку отзыва и поведение при недоступности store. Персональный logout и logout-all должны иметь разные понятные семантики.

Посмотреть AdminUserService, AccountManagementService, RefreshTokenService, AuthController, RequiredActionFilter и SecurityConfig.

Проверить старым JWT после снятия ADMIN, удаления пользователя, password reset, logout-all и добавления required action. Проверить все провайдеры и refresh. Если выбирается допуск до exp, зафиксировать максимальное окно с clock skew и компенсирующие меры для административных действий.

Готово: фактическое время прекращения доступа соответствует документированному требованию.

## 9. Дополнительная проверка production и уведомлений

Это непроверенные направления, не список уже доказанных уязвимостей:

- ProductionSafetyConfig: неверный/отсутствующий профиль, dev-code, console fallback, отсутствие постоянного signing key, слабые cookie-настройки. Проверить реальный контракт starter у consumer, а не только bundled application-prod.yaml.
- Telegram webhook: отсутствующий/неверный secret, повтор update, session ownership, expiry, rate limits и подмена forwarded IP.
- Почта: кому разрешена отправка от домена компании; достаточно ли роли USER; обход per-user quota несколькими аккаунтами и параллельными запросами; лимиты получателей/вложений; SMTP TLS.
- Push: изоляция владельцев токенов, возможность перепривязки чужого устройства, приватные topics, права broadcast, отсутствие утечки history другого пользователя.
- Account recovery: различие ответов для существующего/несуществующего email, смена email/phone без свежего подтверждения личности, отзыв сессий после чувствительных изменений.
- Actuator/Swagger: какие endpoints реально открыты у production-consumer; default chain даёт прочим actuator endpoints authenticated, а не ADMIN. Выбрать осознанную политику.
- Проверить логи и error responses на OTP, tokens, passwords, ключи и чувствительные данные; секреты не выводить в отчёт.
- Проверить свежую БД и обновление существующей PostgreSQL с помощью настоящего Flyway. Текущий CI применяет SQL через psql, поэтому не доказывает работу Flyway history/checksums.

Каждую найденную проблему оформлять: предусловия → воспроизведение → ожидаемый результат → исправление → регрессионный тест. Не расширять scope до переписывания всех модулей без причины.

## 10. Финальная проверка и передача результата

После целевых тестов выполнить на согласованной JDK:

```bash
./mvnw -B --no-transfer-progress clean verify
./mvnw -B --no-transfer-progress dependency:tree -DoutputFile=target/dependency-tree-after.txt
git diff --check
git status --short
```

Также обязательны для затронутых изменений:

- PostgreSQL интеграционные тесты ограничений, транзакций и миграций.
- Consumer tests: автонастройка, замена beans, отключение security/provider, cookie mode.
- Реальная сборка/старт минимального приложения-потребителя с новой версией starter; его собственное dependency tree и SCA.
- Браузерные проверки cookie/CSRF, если этот режим затронут.
- Обновлённые README/config reference и release notes с несовместимыми изменениями и переходом токенов/клиентов.

Финальный отчёт исполнителя должен содержать таблицу:

| Пункт | Статус | Что изменено | Доказательство | Остаточный риск |
|---|---|---|---|---|
| F1–F8 и новые находки | Исправлено / не применимо с обоснованием / требует решения | Файлы | Команда и результат теста | Условия/ограничения |

Критерий готовности: F1/F2 закрыты отрицательными регрессионными тестами; изменения зависимостей проверены; все затронутые контракты и миграции проходят; необработанные риски явно перечислены. «Все тесты зелёные» без тестов атакующих сценариев недостаточно.

## Новые находки после первоначального плана (2026-09-28)

### P0: защита смены email/телефона

Сейчас одного действующего access JWT достаточно, чтобы запросить изменение контакта на адрес/номер атакующего. OTP уходит новому владельцу контакта. После подтверждения включённые по умолчанию email/phone OTP endpoints дают новые access и refresh tokens к прежнему аккаунту без старого пароля или прежнего контакта. Проверить цепочку на локальном и административном пользователе. Исправить: повторно подтвердить существующий фактор непосредственно перед сменой, ограничить срок действия такого подтверждения, подтвердить новый контакт, уведомить старый, отозвать refresh tokens; для немедленного отзыва access JWT применить выбранное решение F6. Регрессионный тест должен доказать, что один украденный JWT и код с нового контакта не дают постоянный доступ.

### P1: политика passwordless для существующих и административных аккаунтов

`UserService.findOrCreateEmailOtpUser` входит в любого существующего пользователя по совпавшему email и наследует его роли, включая ADMIN. Это явная функция passwordless, но для привилегированного аккаунта почта становится единственным фактором. Зафиксировать продуктовую политику: запретить OTP-вход для ADMIN и/или аккаунтов с другими credentials либо требовать дополнительный фактор. Проверить совместимость клиентов.

### P1: конкурирующее обновление refresh token

Запустить два одновременных `/auth/refresh` с одним token на PostgreSQL. Проверить число успешных ответов, число действующих дочерних токенов и поведение grace window/reuse detection. При нарушении инварианта сделать атомарное условное потребление старого token с проверкой числа обновлённых строк.

## Отдельное последующее решение: Keycloak

Этот план укрепляет существующий starter. Для перехода на Keycloak нужен отдельный план: идентификаторы пользователей и связи с бизнес-данными, credentials migration, social accounts, Telegram/WhatsApp, MFA, клиенты/roles/audience, завершение старых сессий, этапность и откат.

До выбора миграции получить ответы: сколько приложений, требуется ли SSO/LDAP/MFA, какие способы входа обязательны, кто будет обслуживать IAM. Не переносить пользователей и не удалять собственную авторизацию в рамках текущего исправления.
